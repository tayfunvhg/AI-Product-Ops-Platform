# Архитектура AI Product Ops Platform

Версия документа: 1.0 · Дата: 2026-05-30 · Статус: черновик для обсуждения

Документ описывает: (1) текущее состояние прототипа, (2) целевую архитектуру
ближайшей итерации («фронт + лёгкий бэкенд», интеграции — заглушки), (3)
перспективную («production») архитектуру с реальными интеграциями, (4) модель
данных, (5) слой адаптеров интеграций, (6) поэтапный план миграции.

---

## 0. Контекст продукта (целостный взгляд)

Платформа — рабочее место Product Owner с встроенными ИИ-агентами (копилотами).
Ключевая идея, вытекающая из всех накопленных требований:

> **Копилоты в едином разделе «ИИ-менеджер» порождают артефакты, которые после
> утверждения PO публикуются в профильные разделы платформы и далее уходят во
> внешние системы (Трекер, Confluence, дашборды).**

Из этого следуют три архитектурных требования, которых нет в текущем прототипе:

1. **Персистентность артефактов.** Видение, метрики/RunRate, гипотезы, персоны,
   фидбэк по гипотезам нужно где-то хранить между сессиями и между разделами.
2. **Модель жизненного цикла артефакта** «черновик → утверждён PO → опубликован».
   Копилот предлагает, человек утверждает, система публикует (slide 5 «человек
   владеет решением»).
3. **Слой интеграций** с внешними системами: Трекер, Insight (продуктовые
   метрики), Qlik + Insight (производственные метрики), Wiki/Confluence.

Разделы платформы и их источники данных:

| Раздел | Что показывает | Кто порождает | Внешний источник/приёмник |
|---|---|---|---|
| Главная | ИЗИ в динамике, рекомендации, дайджест алертов | агрегация | — |
| Видение и стратегия | видение, ставки, цели, материалы | Vision Writer | Confluence (вывод) |
| Гипотезы / Discovery | персоны, исследования, бэклог гипотез | Hypothesis Generator, агент персон | Трекер (двусторонне) |
| Tactical | OKR, бэклог-приоритизация | агент планирования | Трекер |
| Execution | статусы, протоколы | агент исполнения | Трекер |
| Мониторинг | плашки метрик, графики, RunRate-таблица, алерты | агенты-мониторы | Insight, Qlik (ввод) |
| ИИ-менеджер | все копилоты | — | — (хаб) |

## 1. Текущее состояние (factual)

```
Next.js 14 (app router) — монолит, всё в одном процессе
├── src/app/*/page.tsx        — серверные страницы разделов (RSC), читают mock.ts
├── src/app/api/
│   ├── agent/route.ts        — вызов LLM (X5 Copilot) для агентов
│   ├── extract/route.ts      — извлечение текста из PDF/PPTX/MD/изображений
│   └── x5/health/route.ts    — проверка подключения LLM
├── src/lib/
│   ├── x5.ts                 — LLM-клиент (x5/openai/deepseek, ретраи, таймаут)
│   ├── agents.ts             — реестр агентов + загрузка промтов с диска
│   ├── mock.ts               — ЕДИНСТВЕННЫЙ слой данных (статичные сиды)
│   ├── extract.ts            — парсеры файлов
│   └── agentlog.ts           — JSONL-лог обращений к агентам
└── src/components/           — UI (AgentPanel, Sidebar, Markdown, ...)
```

Характеристики:
- **Нет БД, нет персистентности.** `mock.ts` — статичные данные; переписка
  агента хранится в `localStorage` браузера.
- **Бэкенда как отдельного сервиса нет** — только Next.js API-роуты.
- **Интеграций нет** — `SOURCES` в `mock.ts` лишь имитирует список коннекторов.
- Агенты **только возвращают текст** — ничего не мутируют (по дизайну прототипа).

Это здоровая отправная точка: чистый монолит на Next.js, который можно
наращивать инкрементально, не переписывая.

## 2. Целевая архитектура ближайшей итерации («фронт + лёгкий бэкенд»)

Принцип: **остаёмся в монолите Next.js**, добавляем тонкий слой персистентности и
слой адаптеров интеграций с mock-реализациями. Никакого отдельного бэкенд-сервиса
пока не вводим — это преждевременно для прототипа и замедлит итерации.

```
┌─────────────────────────────────────────────────────────────┐
│  Браузер (React 18, client components)                        │
│  — разделы, AgentPanel, графики, таблицы, кнопки публикации   │
└───────────────┬───────────────────────────────────────────────┘
                │ fetch /api/*
┌───────────────▼───────────────────────────────────────────────┐
│  Next.js (app router) — единый процесс                         │
│                                                                │
│  API-роуты (server):                                           │
│   /api/agent          — оркестрация LLM (как сейчас)           │
│   /api/extract        — парсинг файлов (как сейчас)            │
│   /api/artifacts      — CRUD артефактов + публикация  [новое]  │
│   /api/integrations/* — адаптеры (заглушки)           [новое]  │
│                                                                │
│  Слой домена (src/lib):                                        │
│   repo.ts        — репозиторий артефактов (persistence)  [нов] │
│   artifacts.ts   — типы + жизненный цикл (draft→approved→pub)  │
│   parsers/       — парсеры вывода копилотов (vision, runrate,  │
│                    hypotheses) в структурированные артефакты   │
│   integrations/  — адаптеры: tracker, insight, qlik, confluence│
│   x5.ts, agents.ts, extract.ts, agentlog.ts (как сейчас)       │
└───────────────┬───────────────────────────────────────────────┘
                │
┌───────────────▼───────────────────────────────────────────────┐
│  Персистентность (лёгкая)                                      │
│   SQLite (через better-sqlite3) ИЛИ JSON-файлы в /data         │
│   — артефакты, версии, статусы гипотез, фидбэк, материалы      │
│   /data/blobs — загруженные материалы (файлы)                  │
└────────────────────────────────────────────────────────────────┘
                │  (заглушки сейчас, реальные коннекторы позже)
        ┌───────┴────────┬──────────────┬─────────────┐
     Трекер          Insight          Qlik        Confluence
   (Jira и т.п.)  (прод. метрики)  (произв.)     (wiki)
```

### 2.1. Выбор хранилища

Рекомендация — **SQLite (`better-sqlite3`)**:
- одна зависимость, файл на диске, нулевая инфраструктура;
- транзакции и реляционные связи (артефакт → версии → публикации; гипотеза →
  фидбэк) — что нужно для жизненного цикла и истории;
- лёгкая последующая миграция на Postgres (тот же SQL-диалект в основном).

Альтернатива на «совсем лёгко» — JSON-файлы через слой `repo.ts`. Достаточно для
демо, но хуже для связей и конкурентной записи.

> **Решение для прототипа (реализовано):** взяли **JSON-файловое хранилище**
> (`src/lib/store.ts` → файлы в `/data`, gitignored), спрятанное за `repo.ts`.
> Причина — `better-sqlite3` требует нативной сборки (node-gyp), что хрупко в
> текущем окружении и замедляет итерации. JSON-стор — это «лёгкий бэкенд» с
> нулевыми зависимостями, переживает рестарты и поддерживает жизненный цикл
> артефактов. **SQLite/Postgres — drop-in замена за тем же интерфейсом `repo.ts`**
> на этапе F, без правок доменного кода и UI.

### 2.2. Жизненный цикл артефакта

```
копилот (LLM-вывод текстом)
   → parser извлекает структуру → Artifact{status: "draft"}
   → PO жмёт «Опубликовать в раздел»
   → repo: status = "published", пишет в целевой раздел (новая версия)
   → раздел показывает последнюю published-версию
   → (опц.) интеграция: push в Confluence / Трекер
```

Это и есть выбранный механизм («Кнопка „Опубликовать в раздел“»). Публикация —
явное действие PO, с версионированием (можно откатиться/сравнить).

### 2.3. Парсеры вывода копилотов

Каждый копилот возвращает текст в известном формате (мы их зафиксировали в
промтах). Парсер превращает текст в типизированный артефакт:
- **Vision Writer** → блоки: формулировка, «возможности персон», стратегия по
  годам с ориентирами, цели (целевой/база), контекст/риски.
- **Генератор метрик (RunRate)** → таблица: цель → метрики → значения по
  периодам. **Здесь критичен «инвариант парсинга» из промта v2.5** (строка-цель
  жирная с пустыми периодами; строка-метрика с префиксом «— » и заполненными
  ячейками) — парсер опирается ровно на него.
- **Генератор гипотез** → карточки: формулировка, источник, уверенность, метод
  проверки, данные, приоритет.

Парсеры — точка хрупкости (LLM может отклониться от формата). Поэтому:
(1) промты ужесточены под инвариант; (2) парсер устойчив к мелким отклонениям;
(3) перед публикацией PO видит превью артефакта и подтверждает.

## 3. Перспективная («production») архитектура

Когда интеграции пойдут «вживую» и нагрузка/команда вырастут — эволюционируем
монолит, не ломая его:

```
Frontend (Next.js)
   │
API Gateway / BFF (Next.js API или вынесенный Node-сервис)
   │
   ├── Artifact Service      — артефакты, версии, публикации, права
   ├── Agent Orchestrator    — выполнение копилотов, очереди для
   │                           проактивных агентов (гипотезы, мониторинг)
   ├── Integration Service   — коннекторы к внешним системам
   └── Alert/Monitoring      — агенты-мониторы, аномалии, рекомендации
   │
Хранилища: Postgres (артефакты/состояние) · Blob (материалы) ·
            очередь (BullMQ/Redis или брокер) для async-агентов
   │
Внешние системы: Трекер · Insight · Qlik · Confluence
```

Что появляется по сравнению с итерацией:
- **Agent Orchestrator** с очередями — для проактивных агентов, которые работают
  не в чате, а по событию/расписанию (генератор гипотез «предлагаю сам»,
  мониторинг метрик в реальном времени, агент анализа материалов под кнопкой
  «Проанализировать»).
- **Integration Service** — изоляция реальных коннекторов (auth, rate limits,
  ретраи, маппинг схем) от домена.
- **Postgres** вместо SQLite, **Blob-стор** (S3-совместимый) для материалов.

Переход — замена реализаций за уже существующими интерфейсами (`repo.ts`,
`integrations/*`), а не переписывание.

## 4. Модель данных (итерация)

Опираемся на уже существующие типы из `mock.ts`, добавляем артефакты и
жизненный цикл.

```
Artifact
  id, type ('vision'|'metrics'|'runrate'|'hypotheses'|'personas')
  status ('draft'|'approved'|'published')
  payload (JSON — типизированная структура под type)
  source ('copilot'|'manual'|'integration')
  createdAt, createdBy
ArtifactVersion
  id, artifactId, version, payload, publishedAt, publishedBy

Hypothesis (расширяем существующий тип)
  + tag ('proposal'|'accepted')           — воронка «Предложения»
  + decision ('validated'|'rejected'|null)
  + rejectComment                          — фидбэк для калибровки агента
  + confidence ('high'|'medium'|'low')     — из промта генератора
  + verifyMethod, sources[], priorityRank

Material (бывшие «Презентации»)
  id, sectionId, filename, mime, blobRef, uploadedAt, extractedText

MetricSeries (для графиков и RunRate-таблицы)
  metricId, kind ('product'|'production')
  points[] { period, plan, fact }          — план/факт по периодам

IntegrationConnector (развитие SOURCES)
  id, kind ('tracker'|'insight'|'qlik'|'confluence')
  direction ('in'|'out'|'both'), connected, config
```

История ИЗИ уже есть (`HEALTH_INDEX.history`) — для «динамики» на Главной
достаточно расширить до временного ряда с датами.

## 5. Слой адаптеров интеграций

Единый интерфейс, mock-реализация сейчас, реальная — позже. Направление потока:

| Коннектор | Технология | Направление | Что делает |
|---|---|---|---|
| Трекер | Jira-подобный | both | push новых гипотез на доску; сверка/актуализация существующих |
| Insight (продукт) | Insight | in | факт + плановые значения метрик/RunRate → таблица метрик |
| Qlik + Insight (произв.) | Qlik, Insight | in | факт производственных метрик → плашки/столбчатые графики |
| Confluence | Atlassian | out | экспорт видения и др. артефактов в wiki |

Интерфейс (концептуально):

```
interface IntegrationAdapter<TIn, TOut> {
  kind: ConnectorKind
  isConnected(): boolean
  pull?(query): Promise<TIn>     // Insight, Qlik
  push?(artifact): Promise<TOut> // Трекер, Confluence
}
```

Сейчас каждый адаптер — заглушка: `isConnected()` из настроек, `pull/push`
возвращают mock/echo. UI работает полностью, поток данных виден, реальные вызовы
подключаются заменой одной реализации.

**Вопросы по интеграциям — в разделе 7 (нужны от вас перед реальным подключением).**

## 6. Поэтапный план миграции (привязка к мастер-плану)

- **Этап A — каркас данных.** `repo.ts` + SQLite, типы артефактов, жизненный
  цикл, API `/api/artifacts`. Перевести разделы с прямого чтения `mock.ts` на
  репозиторий (mock как сид-данные при первом запуске). *Разблокирует [2], [4], [5], [6].*
- **Этап B — хаб «ИИ-менеджер» [2].** Раздел со всеми копилотами + кнопка
  «Опубликовать в раздел» + парсеры вывода.
- **Этап C — разделы-потребители [3]/[4]/[5]/[6].** UI + чтение published-артефактов.
- **Этап D — слой интеграций (заглушки) [часть 7].** Адаптеры + кнопки
  «Синхронизировать с Трекером», «Вынести в Confluence», «Проанализировать».
- **Этап E — Главная и Execution [8].** ИЗИ в динамике, дайджест алертов, навигация.
- **Этап F (позже).** Реальные коннекторы, очереди, проактивные агенты, Postgres.

## 7. Открытые вопросы (нужны перед реальным подключением интеграций)

1. **Трекер:** какой именно (Jira Cloud/Server, иное)? Есть REST API и тестовый
   проект? Двусторонняя синхронизация — по каким полям сопоставлять задачи?
2. **Insight (продуктовые метрики):** способ доступа — REST API, выгрузка,
   прямое подключение? Формат RunRate (план/факт по периодам) — есть ли схема?
3. **Qlik:** Qlik Sense/QlikView? Доступ через Qlik Engine API / REST / экспорт?
4. **Confluence:** Cloud или Server/Data Center? REST API + пространство для
   публикации? Формат страницы (storage/ADF)?
5. **Аутентификация:** сервисный аккаунт/токены или OAuth от лица PO? Где хранить
   секреты (сейчас `.env.local`)?
6. **Тестовые контуры:** есть ли sandbox-окружения, чтобы отлаживать без
   продакшн-данных и без VPN-зависимости?

Эти вопросы не блокируют этапы A–E (всё на заглушках). Они нужны на этапе F.
