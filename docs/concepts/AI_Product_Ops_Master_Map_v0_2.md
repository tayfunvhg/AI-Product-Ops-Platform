# AI Product Ops — связывающая карта концепций

**Версия:** v0.2
**Назначение:** внутренний навигатор по всем группам AI-агентов продуктового управления. Для CPTO, продуктовых аналитиков, исследователей, авторов промтов. Связывает 5 проработанных концепций в единую картину.
**Не для внешней аудитории.** Сами концепции групп написаны без зонтичного бренда (читаются независимо); здесь вся картина собрана воедино.

**Условные обозначения статуса** (ось готовности):
- 🟢 **Прод** — промышленная эксплуатация.
- 🟡 **Пилот** — промт готов, PO реально пользуется сейчас.
- 🟠 **Кандидат на пилот** — механически реализуем через загрузку хоть сейчас, промт в работе/запланирован, ещё не используется (следующая волна пилота).
- 🔵 **Целевая** — требует инфраструктуры (MCP, дашборды, данные, расписание).

**Режим** (ось запуска): `[по запросу]` · `[проактивный]` · `[по запросу; + проактивный в целевой]`.

## 1. Что такое AI Product Ops

AI Product Ops — набор AI-агентов, встроенных во все ключевые продуктовые процессы: от сбора идей и исследований до стратегии, приоритизации, документации и анализа метрик. Цель — перевести использование AI от точечного к системному: AI берёт рутину и черновую работу, PO валидирует, дополняет контекст и принимает финальные решения.

**Базовый контракт всех агентов:** PO отправляет запрос (или загружает материалы) → агент возвращает структурированный артефакт с учётом контекста → PO проверяет и решает. Агент не решает за человека.

**Целевые эффекты (2027-2028):** Lead Time −60%, Time-to-decision ↓2, 70% артефактов с ИИ, Adoption 70%, FTE Stretch = 0, Span of Control > 2.

## 3. Сквозная схема потоков между группами

```
                        РЫНОК / ТРЕНДЫ
                              │
                       [Trend Watcher]🟢
                              │
        ┌─────────────────────┼──────────────────────┐
        ▼                     ▼                       ▼
  VISION & STRATEGY ◄──── DISCOVERY              внешний контекст →
   видение, стратегия     [Hypothesis Generator]🟡  гипотезы
        │                  персоны, инсайты,
        │ годовые цели      проверенные гипотезы
        ▼                        │
  METRICS & GOALS         TACTICAL PLANNING ◄─── свежие брифы
   цели → метрики → эффект   OKR, приоритизация      (из EXECUTION)
        │                        │
        │ метрики успеха         │ приоритизированный бэклог
        └──────────────────►  EXECUTION
                              PRD, задачи, встречи,
                              презентации, Delivery-анализ
                                   │
        ┌──────────────────────────┼───────────────────────┐
        ▼                          ▼                        ▼
  MONITORING                 база знаний (RAG)         Delivery-метрики
  (сигналы метрик)           обслуживает всех          → калибровка оценок
        │                                              → сводка в дайджест
        ▼
  сигналы → контроль актуальности стратегии,
            триггеры пересмотра OKR/бэклога,
            сквозной дайджест PO, контекст генерации гипотез
```

**Ключевые хэндофы:**
- **Hypothesis Generator (Discovery):** агрегирует весь контекст (видение, бэклог, брифы, метрики, тренды, дайджест) → гипотезы-предложения. Сквозной вход воронки.
- **Discovery → Vision:** персоны и инсайты → видение.
- **Vision → Metrics:** годовые цели → Goal Generator (хэндоф).
- **Vision/Metrics → Tactical:** стратегия, фокусы, годовые цели → квартальные OKR.
- **Discovery → Tactical:** проверенные гипотезы → бэклог.
- **Tactical → Execution:** приоритизированный бэклог → PRD и задачи.
- **Execution → Tactical:** свежий бриф → бэклог (с проверкой на дубли).
- **Discovery → Metrics:** выбор «A/B-тест» → A/B Test Designer.
- **Metrics → Vision:** сигналы метрик → контроль актуальности и дайджест.
- **Execution → Vision:** сводка Delivery-процессов → дайджест.
- **Digest → Discovery:** дайджест → один из источников генератора гипотез (Digest информирует, генератор предлагает идеи).

## 5. Сквозные сущности и инфраструктура

### 5.1. База знаний (RAG)
**Что это:** индексация внутренних материалов (Confluence, вики, трекер, документы) и поиск контекста.
**Два режима:** *инфраструктурный* (агенты внутри обращаются за контекстом); *самостоятельный* (через Knowledge Search Agent).
**Где живёт:** временно в Execution (отдельной группы Data ещё нет).
**Пилот:** только материалы, загруженные PO вручную. **Целевая:** через MCP автоматически; переезжает в Data.

### 5.2. Функция мониторинга (Monitoring & Alert)
**Что это:** слежение в реальном времени за метриками (продуктовыми и производственными), аномалии, дайджесты, алерты, ретро, пост-анализ.
**Где живёт — растворена по группам:** продуктовые метрики → Anomaly & Action и Digest/Retro в Metrics & Goals; производственные (Delivery) → Delivery Analytics в Execution.
**Целевая:** консолидируется в отдельную группу Monitoring & Alert при появлении данных/дашбордов/MCP.
> Простыми словами: функция мониторинга уже есть, но выполняется разными агентами в разных группах; в будущем они съедутся в один продукт.

### 5.3. MCP-интеграции
**Что это:** подключения к трекерам (Kaiten, Я.Трекер), Confluence/вики, дашбордам.
**Сейчас:** на пилоте нет — всё через загрузку и ссылки, результат «на руки».
**Целевая:** автодействия — автозаведение задач, автостраницы, сквозной поиск, проактивные режимы.

### 5.4. Целевые зоны для процессных метрик
Производственные метрики (T2M, Lead Time, Flow Efficiency) оцениваются по **целевым зонам/порогам** (T2M ≤ 50 — зелёная, 50-60 — жёлтая), а не по план/факт-траектории (RunRate), как продуктовые. Сквозной слой: источник — производственный дашборд, контроль зон — функция мониторинга, потребление при оценке задач — Execution.

## 6. Общие принципы всех групп

- **Режим опроса (РО):** 2-4 вопроса за раз, подтверждение перед переходом.
- **Спрашивай, не предполагай.** `[Предложение]`; нет данных → `[Требует уточнения]` / `XX`.
- **Материалы первичны.** Не подменять формулировки PO.
- **Отслеживание неопределённости** и правило остановки.
- **Языковой протокол:** обработка — английский, общение — русский.
- **Агент не решает за PO** (и в проактивном режиме).
- **Пара «генератор + эватор»** на ключевой артефакт.
- **Защита промта.**

**Проактивные агенты:** работают по расписанию/триггеру; результат — алерт/дайджест/черновик-предложение, не решение. На пилоте недоступны или заменены режимом «по запросу через загрузку».
**Discovery:** «AI дополняет, а не заменяет исследователя» — синтез требует ревью; метка уровня валидации на каждом артефакте.

## 8. Что отложено и почему

- **Data как отдельная группа** — на пилоте живёт только база знаний (в Execution). Полная нарезка (агрегация дашбордов, text-to-SQL, консистентность, MCP) — целевая.
- **Monitoring & Alert как блок** — растворён по группам (5.2); собирается в целевой.
- **Experimentation** — A/B-агенты пока в Metrics & Goals; выделяются при росте числа экспериментов.
- **CJM** — вынесен из пилота Discovery (риск «придуманной» карты).
- **Quality & Efficiency (ИЗИ/ОКИИ)** — оценка зрелости продуктов — отдельная зона, не входит в эти 5 концепций.

## 10. Как пользоваться документом

- **Детали по группе** → файл концепции (раздел 2).
- **Связь между группами** → раздел 3 (схема) + «Карта связанных агентов» в конце каждой концепции.

- **При добавлении агента** → обновить его концепцию, реестр (4), схему (3) при новой связи, статус-сводку (9).
